## 一、问题背景

预研02中提到"阶段二"的核心是设备联网采集——裁线机、压接机、导通测试仪等设备的数据自动回传。在预研03（云边协同）中，明确了边缘节点负责设备对接。但具体怎么对接，有三个核心问题需要回答：

1. **MES直接对接设备吗？**——MES应用直接读设备数据，还是中间隔一层？
2. **是否需要中间件？**——IoT数据中台/边缘网关在MES设备对接中扮演什么角色？
3. **常见设备的对接协议有哪些？**——线束行业主流设备的通信协议清单是什么？

这三个问题直接决定了阶段二的架构选型、开发工作量和实施成本。

## 二、问题一：MES是否直接对接设备？

### 2.1 三种架构模式对比

| 模式               | 架构图                      | 复杂度      | 扩展性    | 适用场景           |
| ---------------- | ------------------------ | -------- | ------ | -------------- |
| **A. MES直连设备**   | 设备 ←→ MES应用              | 低（少量设备时） | 差（蜘蛛网） | 设备少（<5台）、协议统一  |
| **B. 边缘网关中转**    | 设备 ←→ 边缘网关 ←→ MES        | 中        | 好      | 多品牌设备混合、新老设备共存 |
| **C. IoT平台+MES** | 设备 ←→ 网关 ←→ IoT平台 ←→ MES | 高        | 极好     | 大型工厂、多系统共用数据   |

### 2.2 直连模式详解

```
┌─────────┐     Modbus/RS232      ┌──────────┐
│ 裁线机   │←─────────────────────→│          │
├─────────┤     OPC UA             │  MES应用  │
│ 压接机   │←─────────────────────→│ (内置     │
├─────────┤     私有协议            │  驱动库)  │
│ 测试仪   │←─────────────────────→│          │
└─────────┘                        └──────────┘
```

**优点**：

- 路径短，延迟低（毫秒级）
- 无额外硬件成本
- 少量设备时开发快

**缺点**：

- MES需要内置每种协议的驱动——Modbus驱动、OPC UA Client、串口通信、各厂商私有协议解析
- 每增加一种新设备，MES就要开发一个新驱动
- MES应用与设备强耦合：设备通信异常可能影响MES整体稳定性
- 无法跨系统复用数据（ERP/WMS等想读设备数据又要单独对接）
- 高频原始数据直接冲击MES数据库

**行业调研结论**：直连模式只在"设备<5台、品牌单一、协议统一"的小场景可行。线束车间通常有裁线机、压接机、测试仪等多品牌设备，直连会导致MES变成一个"设备驱动集合"，业务逻辑被设备对接淹没。

### 2.3 边缘网关模式（推荐）

```
┌─────────┐     RS232/Modbus       ┌──────────────┐    MQTT/OPC UA    ┌──────────┐
│ 裁线机   │←─────────────────────→│              │←─────────────────→│          │
├─────────┤     WPCS/ASCII         │  边缘网关     │   标准化JSON      │  MES应用  │
│ 压接机   │←─────────────────────→│  (协议转换    │←─────────────────→│ (只处理   │
├─────────┤     TCP/IP             │   +数据清洗   │   设备事件        │  业务逻辑) │
│ 测试仪   │←─────────────────────→│   +本地缓存)  │←─────────────────→│          │
└─────────┘                        └──────────────┘                   └──────────┘
```

**核心价值**：

- **解耦**：MES只与网关打交道，用统一协议（MQTT/OPC UA），不关心设备差异
- **协议集中管理**：所有设备驱动在网关上，新增设备只需在网关配置，MES不改代码
- **数据清洗**：网关做原始数据过滤、异常值剔除、时间戳统一，MES拿到的是干净数据
- **断网缓存**：网关本地缓存（SQLite），网络断开时数据不丢，MES崩溃不影响设备采集
- **多系统复用**：网关可同时向MES、ERP、能耗系统分发数据

**实际案例**（行业调研）：

- 华东某PVC管材厂采用边缘网关架构后，OEE统计误差从±8%降至±1.2%
- 某离散制造工厂采用网关后，设备接入新增从"2周开发"降到"1天配置"

### 2.4 IoT平台模式（阶段三+再考虑）

```
设备 ←→ 边缘网关 ←→ IoT云平台 ←→ MES / ERP / WMS / 能耗系统
```

在边缘网关之上再加一层IoT云平台，做设备台账管理、数据标准化、多系统分发。**价值在于"数据全域复用"**——不只是MES用，ERP/能耗/设备运维都从同一数据源取。

**但阶段二不需要**：线束MES阶段二的目标是"设备数据回传到MES"，网关直连MES已足够。IoT平台留到阶段三/四，当客户有多系统数据共享需求时再引入。

### 2.5 结论

> **阶段二采用"边缘网关中转"模式（B），不直连设备（不选A），暂不上IoT平台（C留到阶段三+）。**
>
> MES应用专注于业务逻辑（工单/扫码/追溯/质量），设备协议适配由边缘网关承担。这是行业共识——"让MES做MES该做的事，设备对接交给网关"。

## 三、问题二：是否需要IoT数据中台？

### 3.1 边缘网关 vs IoT数据中台——不是一回事

| 维度     | 边缘网关           | IoT数据中台          |
| ------ | -------------- | ---------------- |
| 部署位置   | 车间现场（边缘侧）      | 云端/数据中心          |
| 核心职责   | 协议转换+数据采集+本地缓存 | 设备台账+数据标准化+多系统分发 |
| 与MES关系 | 数据源（向MES推送）    | 数据中间层（MES从中台拉取）  |
| 引入时机   | 阶段二开始          | 阶段三+（多系统共用数据时）   |
| 硬件成本   | 一台工控机/网关硬件     | 云服务器+运维          |

**关键认知**：边缘网关是"必备硬件"，IoT数据中台是"可选软件层"。

### 3.2 线束MES是否需要IoT数据中台？

**阶段二不需要**，原因：

- 线束MES是唯一的数据消费方，不需要跨系统分发
- 设备数量不多（一条线10-20台设备），网关直连MES足够
- 引入IoT中台会增加云服务器成本和运维复杂度

**需要上IoT中台的信号**（阶段三+评估）：

- 客户要求设备数据同时给ERP/能耗系统用
- 多工厂设备统一管理（跨工厂设备看板）
- 设备预测性维护需要历史数据分析平台
- 客户已有IoT平台，要求MES从中台取数据

### 3.3 阶段二的推荐架构

```
┌─────────────────────────────────────────────────────┐
│                    边缘节点（车间）                     │
│                                                       │
│  ┌──────────┐  标准化JSON/MQTT  ┌──────────────┐     │
│  │  MES应用  │←────────────────→│  设备采集     │     │
│  │ (业务逻辑) │                   │  网关进程      │     │
│  └──────────┘                   │              │     │
│                                  │ ·Modbus驱动   │     │
│  ┌──────────┐                   │ ·串口驱动     │     │
│  │ 同步守护  │                   │ ·OPC UA Client│     │
│  │ 进程      │                   │ ·私有协议驱动  │     │
│  └──────────┘                   │ ·数据清洗     │     │
│                                  │ ·本地缓存     │     │
│  ┌──────────┐                   └──────────────┘     │
│  │ 更新代理  │                         ↑               │
│  └──────────┘                         │               │
│                                  RS232/Modbus/TCP     │
│                                       ↓               │
│                          ┌───┬───┬───┬───┬───┐       │
│                          │裁 │压 │测 │穿 │超 │       │
│                          │线 │接 │试 │栓 │声 │       │
│                          │机 │机 │仪 │机 │波 │       │
│                          └───┴───┴───┴───┴───┘       │
└─────────────────────────────────────────────────────┘
```

**关键设计**：设备采集网关是边缘节点上的**独立进程**，与MES应用、同步守护、更新代理并列。MES通过本地消息队列（MQTT或内部API）订阅设备事件，不直接调设备接口。

### 3.4 设备采集网关进程的职责边界

| 网关负责                        | 网关不负责               |
| --------------------------- | ------------------- |
| 协议解析（Modbus/串口/OPC UA/私有协议） | 工单绑定（MES的业务逻辑）      |
| 数据采集（定时轮询/事件订阅）             | 质量判定（MES判断是否合格）     |
| 数据清洗（异常值过滤/滑动平均）            | 追溯关联（MES关联工单/批次）    |
| 时间戳统一（NTP同步）                | 报工逻辑（MES记录完工）       |
| 本地缓存（断网不丢数据）                | 看板渲染（MES展示数据）       |
| 标准化输出（统一JSON格式推MES）         | 参数下发（MES下发→网关转发→设备） |

**一句话边界**：网关只做"采集+清洗+转发"，MES做"理解+判断+记录"。

## 四、问题三：常见设备的对接协议

### 4.1 线束行业设备通信协议全景

线束车间典型设备的通信能力分三档：

| 档位     | 设备特征     | 通信能力                   | 典型设备                               | 占比     |
| ------ | -------- | ---------------------- | ---------------------------------- | ------ |
| **高端** | 进口全自动设备  | 标准协议（OPC UA/MIKO/WPCS） | Komax Alpha/Gamma系列、Schleuniger全系列 | 15-20% |
| **中端** | 国产全自动设备  | 厂商私有接口（串口/TCP/Excel导入） | 海普锐HPC系列、君权全自动机                    | 30-40% |
| **低端** | 半自动/老旧设备 | 无接口或仅RS232             | 手动压接钳、老式裁线机、君权低端                   | 40-50% |

### 4.2 高端设备协议清单

#### Komax（瑞士，线束设备头部品牌）

| 接口          | 协议                             | 通信方式      | 能力                                           |
| ----------- | ------------------------------ | --------- | -------------------------------------------- |
| **MIKO**    | REST API + MQTT + WS-Discovery | 以太网TCP/IP | 实时数据交换：工单下发、机器状态、参数读取/设置、物料消耗、质量统计、错误信息、用户权限 |
| **WPCS**    | ASCII格式报文                      | 串口/以太网    | 简单的生产数据下发+反馈信息回传（物料消耗/质量统计/机器错误/工单状态）        |
| **QCenter** | 专有软件                           | 以太网       | 压接高度/拉力测量设备集成，目标值与实际值比对，不匹配则不允许开工            |

- 基于开放标准：REST/HTTP下发+MQTT事件推送+WS-Discovery自动发现

## 五、协议适配库架构设计

### 5.1 网关进程架构（四层模型）

基于行业最佳实践，设备采集网关采用四层架构：

```
┌─────────────────────────────────────────────────┐
│                  应用接口层                        │
│   RESTful API / MQTT发布 / Web配置界面             │
│   → 向MES推送标准化事件 / 远程配置 / OTA升级        │
├─────────────────────────────────────────────────┤
│                  协议转换层                        │
│   统一数据模型(UDM) → JSON标准化 → MQTT/OPC UA    │
│   → 数据清洗(异常值过滤/滑动平均) → 时间戳统一       │
│   → 断网缓存(SQLite) → 断点续传                     │
├─────────────────────────────────────────────────┤
│                  驱动适配层                        │
│   ┌─────────┐ ┌─────────┐ ┌──────────┐          │
│   │Modbus    │ │OPC UA   │ │串口通信   │          │
│   │RTU/TCP   │ │Client   │ │RS232/485 │          │
│   └─────────┘ └─────────┘ └──────────┘          │
│   ┌─────────┐ ┌─────────┐ ┌──────────┐          │
│   │MIKO     │ │WPCS     │ │私有协议   │          │
│   │Client   │ │Parser   │ │Lua脚本    │          │
│   └─────────┘ └─────────┘ └──────────┘          │
│                                                   │
│   插件化加载：新增协议只需开发驱动插件               │
├─────────────────────────────────────────────────┤
│                  硬件抽象层                        │
│   UART/SPI/CAN/ETH 硬件接口 → 统一读写原语          │
└─────────────────────────────────────────────────┘
```

### 5.2 统一数据模型（UDM）

所有设备数据统一映射为六元组：

```
{
  "device_id":    "CUT-001",           // 设备ID
  "metric_path":  "cutting/length",    // 测点路径
  "value":         152.3,               // 数值
  "data_type":    "float",             // 数据类型
  "timestamp":    "2026-08-19T14:30:00.000Z",  // 时间戳(NTP同步)
  "quality":      "good"               // 品质码(good/bad/uncertain)
}
```

**不同协议的映射规则**：

| 来源协议       | 原始格式                        | 映射到UDM                                           |
| ---------- | --------------------------- | ------------------------------------------------ |
| Modbus RTU | 寄存器地址40001=1523             | device_id=设备SN, metric_path=从地址映射表查, value=152.3 |
| OPC UA     | NodeId="ns=2;s=Temperature" | metric_path=NodeId路径, value=节点值                  |
| MIKO       | REST响应JSON                  | 按MIKO数据模型继承层级映射                                  |
| WPCS       | ASCII报文                     | 按WPCS字段定义解析后映射                                   |
| RS232私有    | 帧解析(帧头+指令+数据+校验)            | 按协议文档解析后映射                                       |

### 5.3 驱动插件化设计

每种协议封装为独立驱动插件，网关主程序通过统一接口调用：

```
驱动插件接口（所有驱动实现同一接口）:
  - discover()        → 设备发现（如WS-Discovery/Modbus扫描）
  - connect(config)   → 建立连接
  - read(points)      → 读取数据点
  - subscribe(event)  → 订阅事件（如MQTT/OPC UA订阅）
  - write(point, val) → 写入数据（参数下发）
  - disconnect()      → 断开连接
  - health()          → 驱动健康状态

新增设备对接 = 开发一个驱动插件 + 配置设备地址映射表
不需要修改网关主程序和MES应用
```

### 5.4 协议适配库——核心资产

| 驱动             | 覆盖设备                             | 阶段二优先级 | 开发工作量      |
| -------------- | -------------------------------- | ------ | ---------- |
| Modbus RTU/TCP | 通用串口/网口设备（仪表/传感器/老设备）            | P0     | 低（标准库）     |
| RS232通用串口      | 国产中低端设备                          | P0     | 低          |
| OPC UA Client  | Komax新设备/Schleuniger/OPC 40570标准 | P0     | 中          |
| MIKO Client    | Komax Alpha/Gamma/Omega系列        | P1     | 中高         |
| WPCS Parser    | Komax老型号（WPCS接口）                 | P1     | 中          |
| 海普锐私有协议        | 海普锐HPC系列                         | P1     | 高（需抓包/要文档） |
| 自定义ASCII解析     | 其他国产设备私有帧                        | P2     | 高（逐个适配）    |

**行业参考**：合肥迈斯（线束MES专用厂商）宣称"预置上百种线束设备通信协议库，即插即用"——这正是行业专属MES的核心壁垒之一。科美通做设备直连，第一步就是建协议适配库。

## 六、数据采集深度分级

设备对接不是"能读数据"就够了，行业实践分三档：

| 档位          | 采集内容               | 对MES的价值   | 实施难度 |
| ----------- | ------------------ | --------- | ---- |
| **L1 状态采集** | 开机/停机/产量计数         | 设备稼动率统计   | 低    |
| **L2 参数回传** | 裁线长度/压接高度/拉力值/导通结果 | 质量监控+追溯关联 | 中    |
| **L3 闭环控制** | 参数下发/超差停机/参数锁定防篡改  | 质量闭环+工艺合规 | 高    |

### 6.1 L1 状态采集（阶段二优先做）

```
网关 → 设备
  · 定时读取设备状态寄存器（运行/待机/故障）
  · 读取产量计数器
  · 上报设备稼动率

MES价值
  · 看板显示设备实时状态
  · OEE自动计算
  · 故障报警
```

### 6.2 L2 参数回传（阶段二迭代做）

```
网关 → 设备
  · 读取裁线实际长度（与工单要求比对）
  · 读取压接高度/宽度/拉力值（与工艺标准比对）
  · 读取导通测试结果（合格/不合格+具体数值）
  · 读取物料消耗记录

MES价值
  · 压接参数自动关联到追溯记录
  · 超差自动预警
  · 不良品自动标记
  · 追溯数据从"人工录入"升级为"设备自动采集"
```

### 6.3 L3 闭环控制（阶段三）

```
MES → 网关 → 设备
  · 下发裁线长度参数到裁线机
  · 下发压接模具参数到压接机
  · 超差时自动停机
  · 参数锁定：未到首检合格前不允许批量生产

MES价值
  · 工艺参数防篡改
  · 质量异常自动停线
  · IATF16949合规：参数不可手工修改
```

## 七、对接实施流程

### 7.1 新设备接入标准流程

```
① 设备调研
   · 确认设备型号/品牌
   · 获取通信协议文档（向设备厂商索取）
   · 确认接口类型（串口/网口/USB）
   · 确认通信能力（支持哪些协议）
        ↓
② 协议分析
   · 有标准协议？→ 直接用现成驱动
   · 有协议文档？→ 按文档开发驱动插件
   · 无文档？→ 抓包逆向分析报文格式
        ↓
③ 驱动开发/配置
   · 开发驱动插件（或配置Modbus寄存器映射表）
   · 配置设备地址映射表（寄存器地址→测点路径）
   · 本地测试：网关能读到数据
        ↓
④ 数据验证
   · 网关采集 → 对比设备HMI显示值
   · 验证时间戳对齐
   · 验证断网缓存+补传
        ↓
⑤ MES联调
   · MES订阅网关MQTT事件
   · 设备数据关联到工单/批次
   · 看板展示设备实时状态
        ↓
⑥ 现场验收
   · 连续运行24小时无数据丢失
   · 拔网线测试断网缓存
   · 数据准确率>99.5%
```

### 7.2 老旧设备改造方案

对于无数据接口的老设备：

| 改造方案    | 原理                            | 成本 | 适用            |
| ------- | ----------------------------- | -- | ------------- |
| 加装外置传感器 | 在设备关键部位加装计数/压力/位置传感器，接I/O模块   | 低  | 只需要产量计数和状态    |
| 加装PLC中转 | 小型PLC采集设备信号，通过Modbus/OPC UA对外 | 中  | 需要采集多种信号      |
| 串口服务器   | RS232串口转TCP/IP，网关通过网络读取       | 低  | 有RS232但无网口的设备 |
| 视觉识别    | 摄像头识别设备仪表盘读数（OCR）             | 中高 | 完全无接口的老设备     |
| 人工录入兜底  | 工人手动在MES录入设备参数                | 零  | 临时方案/极低频数据    |

**阶段二原则**：能加传感器的不上PLC，能上PLC的不上视觉，实在不行人工录入兜底——不为了一台老设备投入超过设备本身价值的改造成本。

## 九、关键设计决策与风险

### 9.1 关键决策

| # | 决策           | 选择                 | 理由                         |
| - | ------------ | ------------------ | -------------------------- |
| 1 | 直连还是网关       | **边缘网关**           | 解耦、可扩展、MES不背设备驱动包袱         |
| 2 | 网关是硬件还是软件    | **软件进程**           | 跑在边缘工控机上，不额外买网关硬件          |
| 3 | 是否上IoT中台     | **暂不上**            | 阶段二MES是唯一消费方，网关直连够用        |
| 4 | 协议驱动怎么管理     | **插件化**            | 新增协议不改主程序                  |
| 5 | 设备数据怎么推给MES  | **MQTT事件**         | 松耦合、断网不阻塞、支持多订阅者           |
| 6 | 老设备怎么处理      | **传感器/串口服务器/人工兜底** | 不为单台老设备投入超价值改造             |
| 7 | OPC 40570跟不跟 | **跟**              | Komax/Schleuniger标准，未来即插即用 |

### 9.2 风险与对策

| 风险            | 影响    | 对策                                      |
| ------------- | ----- | --------------------------------------- |
| 国产设备厂商不提供协议文档 | 无法对接  | ①抓包逆向 ②通过客户关系向厂商施压 ③串口服务器方案兜底           |
| 设备型号太多驱动开发量爆炸 | 阶段二延期 | 优先做Modbus+串口+OPC UA三种通用驱动，覆盖80%+设备      |
| 网关进程崩溃设备数据丢失  | 数据断档  | 网关本地SQLite缓存+看门狗自动重启                    |
| 时间戳不齐导致数据错配   | 追溯错误  | 网关强制NTP同步，统一用网关时间戳                      |
| 边缘工控机性能不够     | 采集延迟  | RK3588/Intel J4125以上配置，实测3000数据点CPU<35% |
| 客户设备老旧无任何接口   | 无法采集  | 传感器方案或人工录入兜底，不为老设备过度投入                  |

## 十、结论与行动建议

### 10.1 核心结论

1. **MES不直接对接设备**——通过边缘网关进程中转，MES专注业务逻辑，网关专注协议适配。这是行业共识，也是科美通MES保持轻量的前提。
2. **阶段二不上IoT数据中台**——边缘网关直连MES已足够。IoT中台留到多系统共用设备数据时（阶段三+）再引入。
3. **协议适配库是核心资产**——阶段二做Modbus+串口+OPC UA三种通用驱动覆盖大部分设备，MIKO/WPCS/海普锐私有协议按需适配。协议库越积越厚，后来者越难追赶。
4. **OPC 40570是必须跟的牌**——Komax/Schleuniger设备在国内Tier1线束厂渗透率高，跟随这个标准降低进口设备适配成本。
5. **老设备不强求**——能加传感器就加，不能加就人工录入兜底。不为单台老设备投入超过其价值的改造成本。
