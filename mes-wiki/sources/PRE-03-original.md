## 1. 云边职责划分

### 1.1 划分原则：一条黄金法则

> **拔掉网线测试**：如果断网后工人无法扫码、无法看工单、无法报工——这个功能就必须在边缘节点本地运行。

云边划分的本质是**把"确定性执行"和"集中式分析"分离**：

- **边缘**：管"快"——秒级响应的生产操作，断网不能停
- **云端**：管"全"——跨工厂、跨时间的分析与管理，断网可延迟

### 1.2 完整职责矩阵

#### 边缘节点（必须本地运行）

| 功能域 | 具体功能 | 为什么必须在本地 |
|--------|---------|----------------|
| **工单执行** | 工单列表查看、工单详情、工艺路线读取、工序推进 | 工人扫码后必须秒级响应，不能等云端API |
| **扫码流转** | 扫码枪数据采集、条码解析、工序防错校验、物料防错（四码比对）、开工/完工确认 | 扫码响应延迟>500ms工人就会感觉卡顿 |
| **质量管理** | 首检/巡检/完工检记录录入、不良品登记、不良代码选择、返工单生成 | 检验数据不能因断网而丢失 |
| **生产看板** | 实时产量、工单进度、WIP分布、今日异常、不良Top5 | 看板必须实时刷新，不能依赖云端查询 |
| **批次追溯** | 事件流写入（报工/检验/消耗/异常的原始记录） | 追溯数据是生产事件，必须本地先落盘 |
| **标签打印** | 看板标签条码打印、成品SN标签打印、合格证打印 | 打印机连在本地PC上，ZPL指令必须本地发送 |
| **基础数据缓存** | 产品BOM、工艺路线模板、物料主数据、不良代码库的本地副本 | 防错校验需要实时读取BOM，不能跨网络查 |
| **用户与权限** | 本地用户登录、工位权限校验 | 断网时工人仍需登录操作 |
| **设备台账缓存** | 扫码点配置、工位配置、打印机配置 | 这些是本地硬件的配置，天然属于边缘 |

#### 云端（集中管理与分析）

| 功能域 | 具体功能 | 为什么放云端 |
|--------|---------|-------------|
| **主数据管理** | 产品/BOM/工艺路线模板的创建与维护、版本管理、发布 | 主数据是全局的，需要集中管控和版本追溯 |
| **多工厂管理** | 工厂注册、产线配置、跨工厂看板 | 跨工厂视角只能在云端实现 |
| **工单计划** | ERP订单拉取、工单创建、工单下发到边缘 | 工单来源在ERP，云端是ERP和边缘之间的桥梁 |
| **数据归档** | 历史生产数据长期存储、批次追溯全量查询 | 边缘存储有限，历史数据需归档到云端 |
| **分析报表** | OEE分析、不良趋势分析、产量统计、人员绩效 | 分析是跨班次/跨天的聚合计算，适合云端 |
| **ERP集成** | 完工回传ERP、物料消耗同步ERP、BOM从ERP拉取 | ERP在云端或企业内网，MES云端与其对接 |
| **系统配置** | 全局参数配置、功能开关、租户管理 | 配置变更需集中管控，再下发到边缘 |
| **API开放** | 给客户/上层系统的开放API | 外部系统访问入口在云端 |
| **设备协议库管理** | 阶段二设备对接的协议适配包管理和分发 | 协议库是全局资源，版本统一管理 |

#### 边界判断：哪些功能"看起来该在云端，实际该在边缘"

| 功能 | 直觉判断 | 正确判断 | 原因 |
|------|---------|---------|------|
| 工单列表 | 云端有工单数据，应该从云端查 | **边缘缓存** | 工人切换工单时要秒开，不能等网络 |
| BOM防错比对 | BOM在云端管理 | **边缘缓存比对** | 扫码防错必须本地实时，BOM数据预缓存到边缘 |
| 追溯查询 | 数据在云端归档 | **本地写+云端归档** | 写入必须先落本地盘（不丢数据），查询近期数据走边缘、历史数据走云端 |
| 看板数据 | 看板是"报表"应该在云端 | **边缘本地聚合** | 看板要每秒刷新，不能每次都查云端 |
| 用户登录 | 用户管理在云端 | **边缘缓存用户表** | 断网时工人必须能登录 |

### 1.3 数据所有权模型

云边划分的底层逻辑是**数据所有权**——谁产生数据，谁拥有数据，另一个方向只是副本：

```
┌─────────────┐                    ┌─────────────┐
│   边缘节点    │                    │    云端      │
│             │                    │             │
│ 生产事件     │  ── 边缘为主 ──→    │ 生产事件副本 │
│ (报工/检验/  │   增量推送          │ (归档/分析)  │
│  异常/追溯)  │                    │             │
│             │                    │             │
│ 主数据副本   │  ←─ 云端为主 ───    │ 主数据原件   │
│ (BOM/模板/  │   版本下发          │ (创建/管理/  │
│  物料/用户)  │                    │  版本管控)   │
└─────────────┘                    └─────────────┘

核心原则：
  · 生产数据：边缘写原件，云端存副本 → 冲突时边缘优先
  · 主数据：云端写原件，边缘存副本 → 冲突时云端优先
  · 不做双向写：各管各的，不存在同一数据的双端并发修改
```

**这是整个云边协同架构最重要的设计决策**——通过"数据所有权单向"从根源上消除大部分冲突场景。

### 2.2 实时同步（在线状态）

在线时，云端和边缘之间有两条同步通道，各自独立运作：

#### 通道一：主数据下发（云→边缘）

```
触发条件：云端主数据发生变更（BOM更新/工艺模板发布/用户变动）
同步方式：版本号驱动 + 定时拉取
```

| 步骤 | 动作 | 说明 |
|------|------|------|
| 1 | 云端主数据变更，版本号自增（如 v12 → v13） | 每张主数据表带 `version` 字段 |
| 2 | 边缘同步守护进程定时拉取（每30秒/1分钟） | 携带当前本地版本号，只拉增量 |
| 3 | 云端API返回 `since_version` 之后的所有变更 | 增量数据，不是全量 |
| 4 | 边缘写入本地DB，更新本地版本号 | 本地DB的 `meta_sync_state` 表记录各表版本号 |
| 5 | 通知MES应用刷新内存缓存 | 热更新，无需重启 |

**关键设计**：
- 拉取而非推送——边缘主动问"有没有新版本"，云端不主动推。这样即使推送通道异常，边缘也能通过定时拉取自愈
- 增量而非全量——只传 `WHERE version > ?` 的记录，减少带宽
- 版本号而非时间戳——避免时钟不同步问题

#### 通道二：生产事件上报（边缘→云）

```
触发条件：边缘产生生产事件（报工/检验/异常/追溯记录）
同步方式：本地队列 + 批量推送 + 幂等确认
```

| 步骤 | 动作 | 说明 |
|------|------|------|
| 1 | MES应用写入生产事件到本地DB | 同时写入 `sync_queue` 队列表 |
| 2 | 同步守护进程扫描队列，按时间排序批量取出 | 每5秒一批，或满50条一批 |
| 3 | 通过HTTPS POST批量推送到云端API | 每条事件带 `event_id`（UUID），用于幂等去重 |
| 4 | 云端逐条写入云端DB，返回成功/失败的event_id列表 | 云端先检查 `event_id` 是否已存在，存在则跳过（幂等） |
| 5 | 边缘收到确认，将对应记录标记为 `synced=1` | 标记而非删除——保留本地完整记录 |

**关键设计**：
- **幂等性是核心**——网络抖动可能导致重复推送，云端靠 `event_id` 去重，保证同一事件不会被写入两次
- **先写本地再推送**——MES应用写事件时只关心本地DB是否写入成功，不关心云端是否收到。推送是后台异步行为
- **批量而非逐条**——减少网络往返，50条/批比50次单条请求效率高10倍以上

### 2.3 离线状态：断网期间发生什么

```
网络断开
  ↓
同步守护进程检测到连接失败（连续3次心跳超时）
  ↓
进入"离线模式"：
  · MES应用完全无感知——继续往本地DB写数据
  · sync_queue 队列持续堆积，synced=0 的记录越来越多
  · 看板/扫码/报工/检验/追溯全部正常工作
  · 本地DB是唯一数据源，所有读写在本地完成
  ↓
工人无感知，产线继续生产
```

**离线期间的约束**（需在UI上提示）：

| 受影响功能 | 原因 | UI提示 |
|-----------|------|--------|
| 新工单无法从ERP拉取 | 工单来源在云端 | "离线模式：仅可使用已下发到本地的工单" |
| 主数据无法更新 | 无法拉取云端最新版本 | "离线模式：使用本地缓存的主数据" |
| 云端看板看不到实时数据 | 事件未上报 | 管理端看板显示"边缘节点离线，数据待同步" |
| 跨工厂数据不可见 | 云端聚合不可用 | 不影响本工厂操作 |

**离线缓存容量规划**：

```
假设：1条生产事件平均 2KB，日均产生 5000 条事件
  → 日均数据量：5000 × 2KB = 10MB
  → 8小时班次断网：约 1700 条 ≈ 3.4MB
  → 72小时极端断网：约 15000 条 ≈ 30MB

结论：SQLite/PostgreSQL本地存储几十MB毫无压力，
      即使断网一周也只产生约70MB数据，磁盘不是瓶颈。
```

### 2.4 网络恢复：离线数据补传

这是整个机制中最关键的环节——必须保证**零丢失、零重复、按序到达**。

```
网络恢复
  ↓
同步守护进程检测到连接恢复（心跳成功）
  ↓
进入"补传模式"：
  ① 查询 sync_queue WHERE synced=0 ORDER BY created_at ASC
  ② 分批推送（每批50条），携带每条的 event_id
  ③ 云端逐条幂等写入，返回确认
  ④ 边缘标记 synced=1
  ⑤ 重复②-④直到队列清空
  ↓
补传完成，进入正常实时同步模式
  ↓
云端触发"数据追赶"通知：
  · 云端看板自动刷新到最新状态
  · 管理端收到"边缘节点已上线，数据已同步"通知
```

**补传的关键保障机制**：

| 保障点 | 机制 | 解决什么问题 |
|--------|------|-------------|
| **零丢失** | 事件先写本地DB再推送，推送失败记录留在队列 | 网络抖动导致推送失败时数据不丢 |
| **零重复** | 每条事件带UUID，云端写入前检查是否已存在 | 网络超时导致"推送了但没收到确认"时重推不重复 |
| **按序到达** | 按 `created_at` 排序推送，云端按序写入 | 追溯事件链的时序正确性 |
| **断点续传** | 每批推送后立即标记 synced=1，崩溃重启从未同步处继续 | 补传过程中边缘重启不丢进度 |
| **限速控制** | 补传速率限制（如每秒100条），避免冲击云端API | 堆积1万条时不会把云端打垮 |
| **指数退避** | 推送失败时等待1s→2s→4s→8s重试，最多5次 | 网络不稳定时避免疯狂重试 |

### 2.5 同步数据结构设计（表级）

#### sync_queue（边缘侧·同步队列表）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT AUTOINCREMENT | 本地自增ID |
| event_id | UUID | 全局唯一事件ID（幂等用） |
| event_type | VARCHAR(32) | 事件类型：report/inspect/exception/consume/trace |
| event_data | JSON | 事件完整内容（JSON格式） |
| created_at | TIMESTAMP | 事件产生时间（本地时钟） |
| synced | TINYINT DEFAULT 0 | 0=未同步, 1=已同步 |
| synced_at | TIMESTAMP NULL | 同步成功时间 |
| retry_count | INT DEFAULT 0 | 重试次数 |
| last_error | TEXT NULL | 最后一次错误信息 |

#### meta_sync_state（边缘侧·主数据版本追踪表）

| 字段 | 类型 | 说明 |
|------|------|------|
| table_name | VARCHAR(64) | 主数据表名（如 product, bom, routing_template） |
| local_version | BIGINT | 本地当前版本号 |
| last_synced_at | TIMESTAMP | 最后同步时间 |
| record_count | INT | 本地缓存记录数（健康检查用） |

## 3. 边缘节点技术架构

### 3.1 边缘节点部署形态

```
┌─────────────────────────────────────────────────┐
│              边缘工控机 (IPC) / PC Server          │
│              (部署在车间机房或电控柜内)               │
│                                                   │
│  ┌─────────────┐  ┌──────────────┐  ┌─────────┐ │
│  │  MES应用服务  │  │  同步守护进程  │  │ 本地DB   │ │
│  │  (Web Server)│  │ (Sync Daemon)│  │(PG/SQLite)│ │
│  └──────┬──────┘  └──────┬───────┘  └────┬────┘ │
│         │                │                │       │
│         └────────────────┼────────────────┘       │
│                          │                        │
│                   ┌──────┴──────┐                 │
│                   │  操作系统    │                 │
│                   │ (Linux/Win) │                 │
│                   └─────────────┘                 │
│                                                   │
│  网络：局域网网关 → 产线PC → 扫码枪/打印机           │
│  外网：通过工厂路由器 → Internet → 云端             │
└─────────────────────────────────────────────────┘

硬件参考配置：
  · CPU：4核以上（Intel i3/i5 或 工控级同等）
  · 内存：8GB以上
  · 硬盘：128GB SSD以上（本地DB + 日志）
  · 网络：双网口（局域网+外网）
  · 系统：Ubuntu 22.04 LTS / Windows 10 IoT Enterprise
  · 预算：5000-8000元/台
```

### 3.2 技术架构选型

#### 方案对比

| 维度 | 方案A：单体应用 | 方案B：微服务+容器 | 方案C：边缘框架(KubeEdge) |
|------|---------------|-----------------|----------------------|
| 复杂度 | 低 | 高 | 很高 |
| 部署 | 一个进程跑完 | Docker Compose编排 | K8s+KubeEdge边缘节点 |
| 运维 | 零运维 | 需要容器知识 | 需要K8s运维能力 |
| 资源占用 | 512MB内存够用 | 2GB起步 | 4GB起步 |
| 适用规模 | 1工厂1车间 | 多产线 | 多工厂大规模 |
| **阶段一推荐** | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐ |

#### 推荐方案：单体应用 + 进程内模块化

阶段一边缘节点用**单体应用**，不需要微服务/容器/K8s。理由：

1. 一台工控机只服务一个车间，并发量有限（几十个工位PC同时访问）
2. 单体应用部署简单、零运维、重启快
3. 微服务/容器引入的复杂度远大于阶段一的需求
4. 未来需要扩展时，单体→微服务可以渐进式拆分

#### 推荐技术栈

```
┌──────────────────────────────────────────────────────┐
│                    边缘节点技术栈                      │

### 3.3 数据库选型深度分析：PostgreSQL vs SQLite

| 维度 | PostgreSQL | SQLite (WAL) |
|------|-----------|-------------|
| 部署 | 需安装服务 | 零安装，一个文件 |
| 并发写 | 多连接并发写 | 单写者（WAL模式可并发读） |
| 并发量 | 数百连接无压力 | 几十个并发读OK |
| JSON支持 | 原生JSONB，可索引 | 原生JSON，不可索引 |
| 网络访问 | 支持TCP远程连接 | 只能本地文件访问 |
| 数据量上限 | TB级 | 理论280TB，实际百GB级舒适 |
| 运维 | 需要基本DBA知识 | 零运维 |
| 与云端同构 | ✅ 云端也用PG，表结构完全一致 | ❌ 云端PG，需转换 |
| 备份 | pg_dump | 复制文件 |
| **推荐场景** | **阶段一标准方案** | 极小客户/PoC验证 |

**推荐PostgreSQL**，理由：

1. **云边同构**——边缘和云端用同一个数据库，表结构完全一致，同步逻辑最简单（不需要数据格式转换）
2. **JSON支持**——工单工艺实例快照、事件数据都用JSON存储，PG的JSONB可索引查询
3. **并发能力**——产线PC通过浏览器访问边缘服务，边缘服务连PG，几十个并发连接轻松应对
4. **迁移友好**——未来从边缘迁移到云端，或者云端归档，`pg_dump`一键完成

**为什么同步进程要独立**：

| 如果同步逻辑在主进程内 | 如果同步进程独立 |
|---------------------|----------------|
| 主进程崩溃→同步也中断 | 主进程崩溃→同步进程继续工作，队列继续堆积 |
| 同步逻辑出bug影响MES可用性 | 同步出bug不影响工人扫码报工 |
| 主进程重启时同步状态丢失 | 同步进程独立重启，从队列断点继续 |
| 无法独立监控同步健康 | 可独立监控同步进程存活状态 |

## 4. 冲突处理策略

### 4.1 为什么阶段一几乎不会有冲突

上一节"数据所有权模型"已经从根源上消除了大部分冲突：

| 数据类型 | 边缘写 | 云端写 | 冲突可能 |
|---------|--------|--------|---------|
| 生产事件 | ✅ 原件 | ❌ 只接收副本 | ❌ 不可能 |
| 主数据 | ❌ 只读副本 | ✅ 原件 | ❌ 不可能 |
| 工单 | ❌ 只执行 | ✅ 创建/下发 | ⚠️ 见下文 |

**唯一的边界场景：工单状态**。云端创建并下发工单到边缘，边缘执行工单（状态变更：待开工→生产中→已完工）。如果云端同时修改了工单（如取消/改交期），就可能和边缘的状态变更冲突。

### 4.2 工单冲突处理

| 场景 | 处理策略 |
|------|---------|
| 边缘报"已完工"，云端同时取消工单 | **边缘优先**——工单已经生产完了，不能取消，只能标记"完工后取消" |
| 边缘报"生产中"，云端修改交期 | **云端优先**——交期是计划属性，不影响执行 |
| 边缘报"生产中"，云端修改工单数量 | **告警人工介入**——已开工工单不允许改数量，云端操作应被拒绝 |

**实现方式**：工单表带 `status` + `version` 字段。云端修改工单时，API先检查边缘上报的最新状态——如果工单已开工/完工，拒绝修改并提示"工单已进入执行，不可修改"。

### 4.3 冲突处理策略矩阵

| 策略 | 适用场景 | 阶段一是否需要 |
|------|---------|--------------|
| 边缘优先 | 生产数据（报工/检验/异常） | ✅ 默认策略 |
| 云端优先 | 主数据（BOM/模板/物料） | ✅ 默认策略 |
| 版本号拒绝 | 工单状态变更 | ✅ 需要 |
| 时间戳仲裁 | 不适用（已通过所有权分离避免） | ❌ 不需要 |
| 人工介入 | 工单数量变更冲突 | ✅ 简单提示即可 |
| CRDT无冲突合并 | 不适用（MES不需要复杂合并） | ❌ 不需要 |

**关键结论**：阶段一**不需要**引入CRDT、向量时钟、分布式事务等复杂冲突解决机制。通过"数据所有权单向"+工单版本号校验，就能覆盖所有场景。

## 5. 阶段一落地建议

### 5.1 从第一天就要做的

| 事项 | 具体要求 | 后补代价 |
|------|---------|---------|
| 每张生产表带 `synced`/`synced_at` 字段 | 建表时就加，默认0 | 后补要ALTER全表，停机更新 |
| `event_id` UUID主键 | 生产事件用UUID，不用自增ID | 后补要改主键类型，数据迁移 |
| `version` 字段 | 主数据表都带版本号 | 后补要加触发器或应用层改造 |
| 同步守护进程 | 独立进程，从第一天就跑 | 后补要重构应用架构 |
| 健康检查API | `/api/health` 返回同步队列深度 | 后补简单，但越早越好 |
| 边缘配置表 | `edge_config` 存边缘节点信息 | 后补简单 |

### 5.2 阶段一可以简化的

| 事项 | 阶段一简化方案 | 后续演进 |
|------|-------------|---------|
| 同步协议 | HTTP REST API + JSON | 可升级gRPC/Protobuf提升效率 |
| 批量推送 | 50条/批，5秒间隔 | 动态调整批次大小和频率 |
| 监控告警 | 日志文件 + 健康检查API | 接入Prometheus+Grafana |
| 多边缘节点 | 单边缘节点（一个车间一台） | 多节点需考虑负载均衡 |
| 数据归档 | 不做（数据量小，全留本地） | 半年后做定时归档任务 |
| 容灾备份 | 手动pg_dump备份 | 自动备份到对象存储 |

### 5.3 开发优先级

```
Sprint 1 (第1-2周)：
  · 数据库表结构设计（含 synced/version/event_id 字段）
  · 边缘MES应用基础框架（单体应用+本地DB连接）
  · 同步守护进程骨架（心跳检测 + 拉取/推送框架）

Sprint 2 (第3-4周)：
  · 主数据拉取同步（增量版本拉取）
  · 生产事件推送同步（队列+批量+幂等确认）
  · 离线/在线状态机

Sprint 3 (第5-6周)：
  · 补传逻辑（断点续传+重试+限速）
  · 健康检查API
  · 同步监控日志

Sprint 4+：
  · MES业务功能（工单/扫码/看板/质量/追溯）
  · 与云端联调
```

### 5.4 云端同步API设计要点

```

  GET /api/v1/sync/pull?table=product&since_version=12

## 6. 风险与约束

### 6.1 技术风险

| 风险 | 影响 | 应对 |
|------|------|------|
| 边缘工控机硬件故障 | 本地数据丢失 | 定时pg_dump备份到U盘/网络存储；关键事件实时双写（本地+云端，在线时） |
| 时钟不同步 | 事件时序混乱 | 边缘节点配置NTP同步；事件时间戳以本地时钟为准，云端不做时间修正 |
| 离线时间超预期 | 队列堆积过大 | 队列表数据量监控告警；72小时以上需人工介入 |
| 云端API不可用 | 生产事件无法上报 | 边缘不受影响，队列持续缓存；云端恢复后自动补传 |
| 网络频繁抖动 | 同步反复失败 | 指数退避重试；状态机平滑切换 |

### 6.2 架构约束

| 约束 | 说明 |
|------|------|
| 单边缘节点不支持高可用 | 阶段一一台工控机，宕机需人工重启。如需HA可后续加备用节点 |
| 不支持多边缘节点共享数据 | 两个边缘节点之间不直接同步，各管各的车间。跨车间数据走云端聚合 |
| 云端不直接执行生产操作 | 云端管理端只看数据/下发主数据，不直接操作工单执行（避免绕过边缘） |
| 主数据变更不实时生效 | 主数据修改后，最长延迟30秒-1分钟到达边缘（拉取间隔）。急单可手动触发同步 |

### 6.3 不做什么

| 不做的事 | 原因 |
|---------|------|
| ❌ 不做双向实时同步 | 复杂度极高，MES不需要 |
| ❌ 不做分布式事务 | 生产数据所有权单向，不需要跨节点事务 |
| ❌ 不做边缘侧微服务 | 阶段一规模不需要，单体够用 |
| ❌ 不做K8s/容器编排 | 一台工控机跑一个进程，不需要编排 |
| ❌ 不做CRDT/向量时钟 | 数据所有权分离已消除冲突 |
| ❌ 不做边缘AI推理 | 阶段一不涉及AI，阶段四再考虑 |
