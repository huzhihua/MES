## 1. 问题背景

云边协同架构（预研03）确定后，每个客户车间部署一台边缘工控机。随之而来的运维问题：

- **首次部署**：是否需要技术人员现场安装？
- **日常更新**：功能迭代、Bug修复、安全补丁如何送达边缘机？
- **规模化后**：客户超过5家、10家后，逐家上门更新是否可行？

**核心结论（先说答案）**：

| 问题 | 答案 |
|------|------|
| 需要技术人员现场安装？ | **阶段一（前3-5家客户）：是**，实施人员上门。这是刻意的——现场有扫码枪绑定、网络配置、工艺核对等只有人能做的事 |
| 云推送静默更新？ | **阶段一就要具备**。客户超过5家后，没有远程更新能力会被运维拖死 |

两者不是二选一，而是分阶段演进：**首次部署上门 → 日常更新远程推送 → 最终零现场运维**。

## 2. 行业实践调研摘要

### 2.1 主流方案概览

| 方案 | 代表 | 适用 |
|------|------|------|
| 商用设备管理平台 | 研华DeviceOn、映翰通DeviceLive、B&R Software Update Edge Service | 设备量大、跨厂商硬件 |
| IoT云平台OTA服务 | 腾讯云IoT Explorer、阿里云、EnOS Edge | 设备固件级更新 |
| 容器化+镜像仓库 | Docker + 私有Registry + OTA Agent | 应用层更新、多应用并存 |
| 自研轻量更新代理 | 双目录/软链接/A-B分区 + 更新脚本 | 边缘机数量有限（<百台） |

### 2.2 行业共识的关键机制

所有成熟方案都包含以下四件套，缺一不可：

1. **灰度发布**：先1%测试设备 → 观察24-48小时 → 20% → 50% → 全量。"一把梭"全量升级是危险的。
2. **自动回滚**：新版本启动后健康检查（如30秒-5分钟内核心服务不可用），Bootloader/agent自动切回旧版本，确保设备永不"变砖"。
3. **完整性校验**：升级包断点续传 + SHA256校验 + 数字签名验证，防止传输损坏和非法镜像。
4. **双版本存储（A/B分区思想）**：设备上永远保留一个完整可用的旧版本，回滚=切换启动指针，秒级完成。

## 3. 首次部署：为什么阶段一要上门

首次上门不只是装软件，以下事项只能现场完成：

| 事项 | 说明 |
|------|------|
| 硬件就位 | 边缘工控机开箱、接电、入车间网络（IP分配/防火墙放行） |
| 外设配置 | 扫码枪COM口绑定（预研03）、打印机IP配置 |
| 工艺核对 | 预置7工序模板与客户实际工艺差异核对、BOM导入 |
| 联通验证 | 云端可达性测试、同步链路验证、断网演练 |

**努力方向是"零配置交付"（Zero-Touch Provisioning）**：

```
发货前：边缘机预装标准镜像 + 写入注册码
现场：  实施人员通电、插网线
自动：  机器注册到云端 → 云端按设备SN下发该客户主数据包
        （BOM/工艺模板/用户/扫码点配置）
结果：  半天完成全部交付
```

## 4. 远程更新机制设计（阶段一核心）

### 4.1 边缘机进程拓扑

在预研03的两进程（mes-app + sync-agent）基础上，增加第三个独立进程：

```
边缘工控机（Linux，systemd管理）
├── mes-app          ← MES应用（更新目标）
├── sync-agent       ← 数据同步守护进程（更新目标）
└── update-agent     ← 更新代理（火种，逻辑极简、极少变更）
```

**update-agent 职责边界**（只做一件事，越简单越可靠）：

- 心跳上报：版本号 + 硬件健康（CPU/内存/磁盘）
- 检查更新：定时轮询云端待执行任务
- 下载校验：SHA256 + 签名验证
- 执行更新：停服务 → 备份 → 部署 → 迁移 → 启动
- 健康检查：新版核心API可用性探测
- 结果上报：成功/失败 + 日志回传云端

### 4.2 安全更新六步流程

```
① 云端发布新版本（版本号 + 更新包 + 签名 + 升级说明）
        ↓
② 云端创建升级任务（指定设备/分组 + 时间窗口，默认凌晨1-5点）
        ↓
③ 边缘agent在时间窗口内下载更新包
   （断点续传 + SHA256完整性校验 + 签名验证）
        ↓
④ 停旧服务 → 备份当前版本 → 部署新版本 → 启动
        ↓
⑤ 健康检查（关键）：
   - 服务进程存活
   - 数据库连接正常
   - 核心API（扫码/报工）可用
   - 持续观察5分钟
        ↓
⑥ 通过 → 上报成功
   失败 → 自动回滚到备份版本 → 上报失败原因
```

### 4.3 目录布局：双目录 + 软链接（推荐方案）

不用Docker/K8s，用"穷人版A/B分区"实现同等效果：

```
/opt/mes/
├── releases/
│   ├── v1.0.0/     ← 完整应用（旧版本，保留）
│   ├── v1.0.1/     ← 当前运行
│   └── v1.0.2/     ← 新下载待切换
├── current -> releases/v1.0.1   ← 软链接，指向当前版本
├── data/           ← PostgreSQL数据 + 配置 + 日志（独立于版本目录）
└── backup/         ← 更新前的DB备份

更新 = 下载到 releases/vX.Y.Z → 校验 → 停服务 →
       执行DB迁移（先pg_dump备份）→ 切软链接 → 起服务 → 健康检查
失败 = 软链接切回旧版本 → 起服务 → 上报
回滚耗时 ≈ 10秒
```

**优势**：
- 零额外依赖（无需Docker），systemd + ln -sf 即可
- 旧版本永远完整保留（保留最近2-3个版本）
- data目录与代码分离，更新不动数据

### 4.4 数据库Schema迁移（最大的坑）

应用更新简单，**DB迁移是边缘更新最大的风险点**。四条规则：

| 规则 | 说明 |
|------|------|
| 迁移脚本随版本包走 | 更新包内含 `migration.sql`，执行前先 `pg_dump` 备份 |
| **只加不改** | Schema变更只允许加列/加表/加索引，不删不改（向前兼容），保证旧应用能连新库 |
| 事务执行 | 迁移在事务中跑，失败则整个更新回滚（应用+DB一起退） |
| 版本双向校验 | 应用启动时校验DB schema版本号，不匹配拒绝启动（防止新应用连旧库、旧应用连新库） |

### 4.5 update-agent 主循环（逻辑规格）

```
每60秒   → 心跳上报（版本/磁盘/CPU/内存）
每5分钟  → 查询云端有无本机待执行任务

有任务且在时间窗口内：
  1. 下载更新包（断点续传，失败重试3次带退避）
  2. SHA256 + 签名校验
  3. 检查磁盘剩余空间（> 更新包3倍）
  4. 备份数据库（pg_dump → backup/）
  5. 停 mes-app / sync-agent
  6. 部署新版本到 releases/vX.Y.Z
  7. 执行DB迁移脚本（事务）
  8. 切软链接 → systemd 起服务
  9. 健康检查（5分钟内多次探测核心API）
  10. 成功 → 上报 + 清理旧备份（保留最近1个版本）
      失败 → 自动回滚 → 上报失败 + 停止重试（等人工介入）
```

## 5. 云端管理功能（阶段一最小版）

四张表 + 一组API，工作量不大，但**从第一天就要有**——没有它，连"哪些客户跑的哪个版本"都不知道：

| 功能 | 内容 |
|------|------|
| 版本管理 | 上传更新包、发布/撤回版本、更新说明 |
| 设备管理 | 每台边缘机：SN、客户归属、当前版本、最后心跳、在线状态 |
| 升级任务 | 选设备/分组、设时间窗口、发起/中止/重试 |
| 升级日志 | 每台设备升级历史、成功/失败、失败原因、agent日志回传 |

**核心数据表（示意）**：

```
edge_device        边缘设备台账（SN/客户/型号/状态/当前版本）
release            版本发布（版本号/包URL/SHA256/签名/说明/状态）
upgrade_task       升级任务（版本/设备列表/时间窗口/状态）
upgrade_log        升级执行记录（设备/任务/结果/失败原因/日志）
```

## 6. 更新时机与生产保护

**更新绝对不在生产时间执行**，即使技术上可以：

| 保护机制 | 说明 |
|---------|------|
| 时间窗口 | 默认凌晨1-5点，云端任务可指定 |
| 在制工单检查 | agent执行前检查是否有执行中工单（可选：有则顺延一晚） |
| 车间确认（可选） | 阶段一可在边缘管理页提示"有新版本，今晚2点更新"给车间管理员 |
| 带宽控制 | 更新包几十MB，多台边缘机分批推送，避免同时下载冲击云端带宽 |

## 7. 灰度发布策略（客户10+家后启用）

```
新版发布
  → 第1家：测试客户（自有演示机或关系最好的客户）
  → 观察48小时（升级成功率 + 运行异常 + 云端报错率）
  → 无异常 → 推送20%客户 → 再观察24小时
  → 全量推送
  → 单台失败设备：自动回滚 + 不再自动重试 + 人工排查
```

**灰度样本选择注意**：测试客户要覆盖不同硬件批次、不同网络环境，只挑网络好环境稳的客户做灰度等于没做。

**版本碎片控制**：灰度要设明确的观察周期、晋级条件、回退条件；超期无法确认的版本暂停扩散，避免多版本长期混跑导致平台无法解释节点间行为差异。

## 8. 离线节点处理

边缘机可能升级时离线（车间断网/关机）：

- **任务不丢失**：云端任务挂起，设备下次心跳上线时领取
- **跳版升级**：设备错过多个版本时，不逐版补装，直接升到目标版本（要求每版migration幂等可跳——"只加不改"规则保证这一点）
- **兼容窗口检查**：跨多个大版本升级前，agent校验目标版本与当前DB schema的兼容性，不兼容则拒绝并上报

## 9. 演进路线

```
阶段一（现在，客户<5家）
  首次部署：实施上门（半天，目标零配置交付）
  日常更新：云端推送 + 静默更新 + 自动回滚 ✓
  更新对象：mes-app + sync-agent + DB迁移
  管理功能：版本/设备/任务/日志 四张表最小版

阶段二（客户10+家）
  + 灰度发布（测试客户→20%→全量）
  + 配置集中下发（扫码点配置/BOM模板批量更新，走主数据通道）
  + 远程诊断（云端SSH反向隧道到边缘机，80%问题免现场）
  + 升级失败自动告警（短信/企微通知运维）

阶段三（规模化，50+台）
  + 容器化（Docker镜像+私有Registry），更新=换镜像
  + 差分更新（只下发变更文件，节省带宽）
  + 设备分组/区域批量操作
  + 可评估商用平台（DeviceOn等）替代自研
```

**容器化不用急着上**：双目录+软链接方案在几十台规模完全够用；Docker的隔离与标准化价值要到上百台、多应用（阶段二设备采集程序等）并存时才真正体现。

## 11. 风险与对策

| 风险 | 对策 |
|------|------|
| update-agent自身Bug导致无法更新 | agent逻辑极简；保留SSH远程通道兜底；agent变更单独灰度 |
| DB迁移失败且备份损坏 | 迁移前pg_dump强校验；迁移在事务内；回滚连带恢复备份 |
| 更新后数据同步不兼容（边缘新版/云端旧版） | 版本协议号机制：同步API带版本协商，云端先升级、边缘后升级 |
| 带宽/流量受限客户 | 差分包（阶段三）；分批推送；时间窗口避开生产 |
| 边缘机被客户IT拦截外网 | 部署时确认白名单；支持离线更新包（U盘导入，阶段一兜底） |
| 半夜升级失败无人知晓 | 失败自动回滚保生产 + 云端告警次日处理（生产保护优先于升级成功） |

---

## 12. 结论

> **首次部署上门是刻意的**（扫码枪/网络/工艺核对只有人能做），**日常更新必须从第一天就是云端静默推送**。边缘机跑独立的update-agent，走"下载→校验→备份→迁移→切换→健康检查→失败自动回滚"流程，用双目录+软链接实现秒级回滚，DB迁移遵循"只加不改、事务执行、版本双向校验"三原则。云端配"版本/设备/任务/日志"四张表最小管理版，客户过5家后启用灰度发布。核心设计信条：**宁可更新失败一百次自动回滚，不可让一次更新导致停线。**
