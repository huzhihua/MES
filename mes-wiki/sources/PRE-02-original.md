## 一、为什么单独拎出技术要点

工序流程配置解决了"做什么"的问题。但MES系统从设计到落地，还有一堆"怎么做才不翻车"的技术决策点。这些点如果在开发前没想清楚，后期改造代价极大——轻则性能瓶颈、重则推倒重来。

本文梳理了 **9个关键技术要点**，每个要点明确：问题是什么 → 行业实践怎么做 → 阶段一怎么做 → 后续怎么演进。

## 二、扫码体系设计

### 2.1 问题

线束车间扫码场景密集——裁线看板标签、压接四码防错、总装板位码、电测结果码、成品SN码……高峰期每分钟扫码数十次。扫码体系设计不当会导致：丢码、重扫、焦点丢失、多枪冲突。

### 2.2 扫码枪接入方式对比

| 方式 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **键盘模拟** | 扫码枪被识别为HID键盘，扫码=模拟键盘输入 | 即插即用，零开发量 | 依赖输入框焦点，多枪无法区分，无法传元数据 | 阶段一MVP |
| **串口通信** | 通过RS232/虚拟串口接收数据 | 不依赖焦点，可控制扫码枪（亮灯/蜂鸣），可区分多枪 | 需配置端口/波特率，需开发监听程序 | 阶段一进阶 |
| **SDK/API集成** | 调用扫码枪厂商SDK | 功能最全（批量模式、连续读、图片采集），可区分任意数量设备 | 开发量最大，绑定厂商 | 阶段二+ |

### 2.3 阶段一建议

| 决策 | 建议 |
|------|------|
| 接入方式 | **键盘模拟为主**，Web端用隐藏输入框+全局监听捕获扫码事件 |
| 防重扫 | 同一码 **5秒内重复扫自动拦截**（前端去重） |
| 焦点管理 | 扫码页面始终维持一个隐藏input获取焦点，扫码后自动回焦 |
| 多枪场景 | 一台PC接多枪时，键盘模拟无法区分来源——需上串口方案或每工位一枪一PC |
| 移动端 | 微信小程序/PDA通过 `wx.scanCode` 或系统摄像头扫码，不依赖外接扫码枪 |

### 2.4 后续演进

- 阶段二：串口通信方案，支持工业扫码枪的蜂鸣/指示灯控制
- 阶段三：设备工位自动触发扫码（PLC到位信号→触发扫码器），无需人工操作

## 三、并发控制

### 3.1 问题

多个工位同时扫码报工、多个班组长同时操作同一工单、看板实时刷新与报工写入冲突——并发处理不当会导致：
- 工单状态被覆盖（A刚报完工，B的旧操作把它改回"进行中"）
- 库存扣减超卖（两人同时领料，系统扣了两次）
- 数据库死锁（多行并发争抢）

### 3.2 行业实践

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| **乐观锁** | 记录带version字段，更新时校验version，冲突时重试 | 读多写少，冲突概率低 |
| **悲观锁** | 更新前先锁定记录，其他事务等待 | 写冲突频繁的关键业务 |
| **分布式锁** | Redis分布式锁，跨服务互斥 | 跨服务共享资源（如排程） |
| **事件追加** | 不UPDATE状态，只INSERT事件记录，状态=事件聚合 | 高并发工序流转 |

### 3.3 阶段一建议

| 场景 | 策略 |
|------|------|
| 工单状态流转 | **乐观锁**（工单表加version字段，报工更新时校验） |
| 工序报工写入 | **事件追加模式**——不UPDATE工单状态，INSERT报工记录，状态由报工记录聚合计算 |
| 物料扣减 | **乐观锁 + 前置校验**（扣减前校验余量≥需求量） |
| 看板数据读取 | 读报工记录聚合，不读工单状态字段（避免读写冲突） |

> **关键原则**：生产数据是"追加"的，不是"修改"的。每一次报工、检验、异常上报都是一条不可变的事件记录。工单"当前状态"是事件流的聚合结果，不是某个字段的值。这避免了绝大部分并发冲突。

### 3.4 后续演进

- 阶段二：引入消息队列（如RabbitMQ）削峰填谷，高频报工异步写入
- 阶段三：分布式锁用于排程互斥、设备参数下发互斥

## 四、离线容灾

### 4.1 问题

车间网络环境远差于办公区——WiFi信号死角、交换机重启、服务器维护、运营商断网……MES系统一旦断网就停摆，产线就得停机等网络恢复。这是车间MES最常被吐槽的问题。

### 4.2 行业实践

| 方案 | 说明 | 效果 |
|------|------|------|
| **边缘服务器** | 车间部署本地服务器，核心功能（扫码/报工/打印）本地闭环 | 断网不停产 |
| **本地缓存+断网续传** | 客户端/终端本地SQLite缓存，网络恢复后自动同步 | 轻量级，无额外硬件 |
| **PWA离线** | Web端用Service Worker缓存关键页面和数据 | 无需安装客户端 |
| **任务预加载** | 联网时预加载工单/工艺/物料规则到本地 | 断网后仍可执行 |

### 4.3 阶段一建议

| 决策 | 建议 |
|------|------|
| 架构 | **本地缓存+断网续传**（轻量方案，无需额外硬件） |
| 缓存内容 | 当前工单信息、工艺路线快照、物料防错规则、BOM清单 |
| 缓存方式 | Web端用IndexedDB/localStorage；小程序用本地存储API |
| 断网行为 | 扫码/报工/检验数据写入本地队列，界面提示"离线模式" |
| 恢复同步 | 网络恢复后自动上传，按时间戳顺序回放，服务端去重（幂等） |
| 冲突处理 | 以服务端为准，本地冲突数据标记为"待人工确认" |
| 离线时长 | 支持 **至少4小时离线运行**（覆盖一个班次） |

> **关键约束**：离线模式下仍需保证扫码防错功能正常——防错规则必须预加载到本地。但"新增工单""修改工艺路线"等管理操作不允许离线执行。

### 4.4 后续演进

- 阶段二：车间部署边缘服务器，实现核心生产功能完全本地化
- 阶段三：云边协同——边缘负责实时控制，云端负责数据分析与全局看板

## 五、标签打印体系

### 5.1 问题

线束行业标签类型多——看板标签（裁线下线流转凭证）、端子标签、成品SN标签、合格证、包装标签……每类标签模板不同、打印时机不同、打印机可能不同。打印体系设计不当会导致：贴错标签、模板版本混乱、打印瓶颈卡住产线。

### 5.2 线束行业标签清单

| 标签类型 | 打印时机 | 内容 | 打印机 |
|---------|---------|------|--------|
| **看板标签** | 裁线下线开工时 | 工单号、线号、导线规格、长度、端子、数量 | 工位旁条码打印机 |
| **端子标签** | 压接工序（可选） | 端子型号、供应商批次、压接参数 | 工位旁条码打印机 |
| **成品SN标签** | 导通测试通过后 | 产品SN码（一物一码）、工单号、日期 | 测试工位打印机 |
| **合格证** | 外检通过后 | 产品型号、检验员、日期、批次 | 外检工位打印机 |
| **包装标签** | 包装入库时 | 包装规格、数量、客户、收货地址 | 包装区打印机 |

### 5.3 阶段一建议

| 决策 | 建议 |
|------|------|
| 打印机通信 | **TCP/IP直连**（9100端口），不依赖打印服务器 |
| 指令集 | **ZPL II**（斑马/兼容打印机通用），模板存为ZPL字符串 |
| 模板管理 | 模板存数据库（含变量占位符），按产品/标签类型绑定 |
| 触发方式 | 工序完工确认后自动触发对应标签打印 |
| 变量替换 | MES下发工单数据→替换ZPL模板中的占位符→发送到打印机 |
| 防错 | 打印前校验：当前工单状态是否允许打印该标签；打印后记录打印日志 |
| 重打控制 | 允许重打但必须填原因，记录重打次数和操作人 |

> **关键原则**：MES决定"什么时候打、打什么内容"，打印机只负责"怎么打"。不在MES里硬编码打印机IP——打印机配置存数据表，换打印机改数据不改代码。

### 5.4 后续演进

- 阶段二：引入打印中台，统一管理多台打印机的状态监控、耗材预警、任务队列
- 阶段三：PLC联动自动打印（工序完工信号→自动触发打印，无人值守）

## 六、权限与数据隔离

### 6.1 问题

线束工厂常见的权限问题：
- 操作工只能看自己工单的数据，班组长能看整个班组
- 不同车间的数据互相隔离，但厂长能看全厂
- 质量数据全员可查，但成本数据仅财务可见
- 客户审核时需要冻结部分操作权限

### 6.2 行业实践：RBAC + 数据权限

```
权限 = 功能权限（能做什么操作） × 数据权限（能看到哪些数据）

功能权限（RBAC）：
  角色 → 权限点 → 菜单/按钮/API
  如：操作工角色 → 扫码报工、查看本工单
      班组长角色 → + 查看班组所有工单、异常处理
      工艺工程师 → + 工艺路线配置、检验标准维护

数据权限（行级过滤）：
  组织维度 → 工厂/车间/产线/工位
  业务维度 → 工单/产品/客户
  如：操作工只能看到分配给自己的工单
      班组长能看到本班组所有工单
      厂长能看到本厂所有工单
```

### 6.3 阶段一建议

| 决策 | 建议 |
|------|------|
| 权限模型 | **RBAC**（角色-权限-用户三层） |
| 数据隔离维度 | **工厂ID + 车间ID** 作为全局过滤标识，所有业务表带这两个字段 |
| 角色预置 | 操作工、班组长、工艺工程师、质量工程师、管理员 5个标准角色 |
| 数据权限 | 行级过滤：用户绑定组织节点，查询自动注入组织过滤条件 |
| 字段权限 | 阶段一暂不做（成本字段等敏感数据不展示即可） |
| 审计日志 | 关键操作（开工/完工/配置变更/重打）全部记录操作人+时间+内容 |

> **关键设计点**：所有业务表从一开始就带 `factory_id` 字段，即使阶段一只有一个工厂。这是数据隔离的基础，后补代价极大。

### 6.4 后续演进

- 阶段二：字段级权限（成本字段仅财务可见）
- 阶段三：跨工厂权限（集团管理员看所有工厂，分厂长只看本厂）
- 远期：多租户SaaS模式（不同企业数据完全隔离）

## 七、追溯数据模型

### 7.1 问题

追溯是MES的核心价值之一。线束行业要求"从原材料批次到成品SN全链路可追溯"，且要求正反向双向追溯。数据模型设计不当会导致：追溯链断裂、查询超时、数据不一致。

### 7.2 行业实践：事件驱动 + DAG

```
传统做法（错误）：
  工单表里存"使用的物料批次"字段 → 查追溯就是查工单表
  问题：多物料多批次无法表达，历史修改丢失，并发冲突

正确做法（事件追加 + 关系链）：

  物料批次 ──消耗──→ 工序报工记录 ←──产出──→ 成品SN
      │                    │                      │
      │                    ├──作业人               │
      │                    ├──设备                  │
      │                    ├──检验结果              │
      │                    └──工艺参数              │
      │                                           │
      └────── 反向追溯 ──────────────────────────→
                       ←──── 正向追溯 ────────────
```

### 7.3 阶段一建议

| 追溯维度 | 数据来源 | 存储方式 |
|---------|---------|---------|
| **人** | 报工记录的作业人字段 | 事件记录 |
| **机** | 报工记录的设备字段（阶段一人工选设备） | 事件记录 |
| **料** | 物料消耗记录（物料批次→工单→工序） | 关系表 |
| **法** | 工单工艺实例快照（当时走的什么工艺） | JSON快照 |
| **环** | 报工时间戳（可关联车间温湿度，阶段一不接） | 事件记录 |
| **测** | 检验结果记录（检验项→实测值→判定） | 事件记录 |

| 追溯方向 | 查询逻辑 |
|---------|---------|
| **正向追溯** | 成品SN → 报工记录 → 物料消耗记录 → 物料批次 → 供应商 |
| **反向追溯** | 物料批次 → 物料消耗记录 → 报工记录 → 成品SN → 工单 |

> **关键原则**：追溯数据是"只追加"的——报工记录、检验记录、物料消耗记录一旦写入不可修改。需要更正时追加一条更正记录，原记录保留。这是IATF16949对追溯数据不可篡改的要求。

### 7.4 后续演进

- 阶段二：设备参数快照存入追溯链（压接力曲线、裁线长度实测值）
- 阶段三：追溯数据上链/存审计库，满足更高合规要求

## 八、编码体系

### 8.1 问题

线束行业涉及的编码对象多——产品、物料、BOM、工单、工序、批次、SN、设备、工位、人员……如果编码规则不统一，追溯链就断了，ERP/MES数据就对不上。

### 8.2 阶段一建议

| 编码对象 | 编码规则示例 | 说明 |
|---------|-------------|------|
| **产品编码** | WH-A2100 | 产品型号，与ERP一致 |
| **物料编码** | WIRE-FLRYB-0.5-GR | 物料分类+规格+颜色 |
| **物料批次** | SUP-20260816-001 | 供应商-到货日期-流水号 |
| **工单号** | WO-20260816-001 | 日期+流水，全局唯一 |
| **工序编码** | OP01_CUT / OP02_CRIMP | 序号+类型缩写 |
| **成品SN** | SN-20260816-A2100-0001 | 日期+产品码+流水，一物一码 |
| **看板标签码** | KB-WO20260816001-01 | 工单号+扎序号 |
| **设备编码** | EQ-KM-001 | 类型+流水 |
| **人员编码** | EMP-001 | 与HR系统一致 |

> **关键原则**：
> 1. 所有编码全局唯一，不可重复
> 2. 编码规则在系统初始化时定义，存数据字典表，不在代码里写死
> 3. 编码生成规则可配置（前缀/日期/流水位数/校验位）
> 4. 物料编码必须与ERP保持一致——MES不自己发明物料编码

### 8.3 编码生成方式

| 方式 | 适用 | 阶段一建议 |
|------|------|---------|
| 自动生成 | 工单号、批次号、SN | 按规则自动生成，用户不干预 |
| 手动录入 | 产品编码、物料编码 | 实施时从ERP导入，日常维护手动 |
| 混合 | 看板标签 | 系统生成工单部分，手动指定扎序号 |

## 九、ERP集成

### 9.1 问题

MES不是孤立系统——需要从ERP接收生产订单和BOM，向ERP回传完工数量和物料消耗。集成设计不当会导致：数据不一致、接口超时、ERP压力过大。

### 9.2 阶段一建议

| 集成项 | 方向 | 方式 | 频率 |
|--------|------|------|------|
| 生产订单 | ERP→MES | API拉取 | 定时（每天3-4次）或手动触发 |
| BOM/物料主数据 | ERP→MES | API拉取/文件导入 | 定时同步 |
| 完工回传 | MES→ERP | API推送 | 报工确认后实时推送 |
| 物料消耗 | MES→ERP | API推送 | 报工时同步推送 |
| 库存同步 | 双向 | API查询 | 实时查询（不缓存库存） |

> **关键原则**：
> 1. MES不替代ERP做库存管理——MES只记录"用了多少料"，库存账以ERP为准
> 2. 接口设计幂等——同一笔完工回传推送多次，ERP只入一次
> 3. 接口失败重试——MES本地队列缓存未推送成功的回传，定时重试
> 4. 阶段一ERP对接可以简化——如果客户暂无ERP，支持Excel导入工单和BOM

### 9.3 后续演进

- 阶段二：实时库存联动（MES领料→ERP实时扣库存）
- 阶段三：双向SOA集成，ERP变更自动通知MES

## 十、性能与可用性

### 10.1 问题

MES是生产系统的命脉，宕机=停产。同时车间高并发扫码对性能要求高。性能问题通常在数据量积累后爆发——上线3个月一切正常，半年后工单列表查询从200ms飙到3秒。

### 10.2 阶段一建议

| 维度 | 要求 | 手段 |
|------|------|------|
| **可用性** | 99.5%（月停机≤3.6小时） | 应用双节点部署 + 数据库主从 |
| **扫码响应** | 扫码到界面反馈 ≤ 500ms | 前端即时反馈 + 后端异步写入 |
| **工单列表查询** | ≤ 500ms（1万条工单） | 索引优化 + 分页 + Redis缓存 |
| **看板刷新** | ≤ 2秒 | 预聚合 + WebSocket推送 |
| **追溯查询** | ≤ 2秒（单SN全链路） | 事件表索引 + 关系表冗余 |
| **并发** | 50并发用户 | 连接池调优 + 静态资源CDN |

## 十三、结论与建议

### 13.1 核心结论

1. **事件追加是MES数据模型的基石**——报工/检验/消耗/异常都是不可变事件，状态是聚合结果。这一条解决了并发、追溯、审计三大问题
2. **factory_id从第一天就要带上**——权限隔离的基础，后补代价极大
3. **离线能力是车间MES的刚需**——不是可选项，是必选项
4. **打印体系要和MES解耦**——MES决定"打什么"，打印模块决定"怎么打"
5. **编码体系必须与ERP对齐**——MES不自己发明物料编码
